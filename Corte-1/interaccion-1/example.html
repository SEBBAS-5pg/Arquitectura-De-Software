Factory vs Singleton en Sistemas Distribuidos

Patrones Escalabilidad Microservicios

En sistemas distribuidos grandes, Factory suele ser más crítico para la escalabilidad que Singleton. Factory permite instancias dinámicas y polimórficas sin estado global; Singleton introduce cuellos de botella y problemas de concurrencia si es mutable.

1) Anti‑ejemplo: Singleton con estado global (riesgo en distribuido)

Problemas típicos: race conditions, acoplamiento global, dificultad para testear y cuello de botella.

// ⚠️ Singleton: una única instancia global compartida (anti‑patrón si hay estado mutable)
const PaymentCounterSingleton = {
  totalProcesados: 0, // ← estado global compartido (peligroso)
  procesar(monto) {
    // Imagina múltiples hilos/requests llamando esto al mismo tiempo:
    this.totalProcesados = this.totalProcesados + 1; // ← race condition
    print("Pago de " + monto + " | total: " + this.totalProcesados);
  }
};

// En microservicios:
// - Cada pod tendría SU propio contador (inconsistente).
// - Si centralizas el estado, creas un cuello de botella.
// - Testing es difícil: no puedes "resetear" fácilmente lo global.
PaymentCounterSingleton.procesar(100);
PaymentCounterSingleton.procesar(50);

2) Enfoque recomendado: Factory (instancias por necesidad, sin globales)

Factory encapsula la creación, respeta SRP/Open‑Closed y facilita polimorfismo en runtime.

// 1) Contrato común (interfaz mental)
interface ProcesadorPago {
  pagar(monto): Recibo
}

// 2) Implementaciones concretas, sin estado global
class PagoTarjeta implements ProcesadorPago {
  pagar(monto) { return Recibo("tarjeta", monto) }
}
class PagoBilletera implements ProcesadorPago {
  pagar(monto) { return Recibo("billetera", monto) }
}

// 3) Factory: decide qué crear SIN que el cliente conozca clases concretas
class ProcesadorPagoFactory {
  crear(tipo) {
    if (tipo == "tarjeta")   return new PagoTarjeta()
    if (tipo == "billetera") return new PagoBilletera()
    throw Error("Tipo no soportado: " + tipo)
  }
}

// 4) Servicio de dominio (cliente) — depende de la interfaz y la factory
class CheckoutService {
  constructor(factory) { this.factory = factory }
  cobrar(tipo, monto) {
    const proc = this.factory.crear(tipo) // nueva instancia si hace falta
    return proc.pagar(monto)
  }
}

// Uso (cada request puede crear su instancia, evitando estado compartido)
const checkout = new CheckoutService(new ProcesadorPagoFactory())
checkout.cobrar("tarjeta", 100)
checkout.cobrar("billetera", 50)

3) Extender sin romper (OCP): agregar PagoCripto

El cliente no cambia; solo se extiende la Factory.

class PagoCripto implements ProcesadorPago {
  pagar(monto) { return Recibo("cripto", monto) }
}

class ProcesadorPagoFactory {
  crear(tipo) {
    if (tipo == "tarjeta")   return new PagoTarjeta()
    if (tipo == "billetera") return new PagoBilletera()
    if (tipo == "cripto")    return new PagoCripto()   // ← extensión mínima
    throw Error("Tipo no soportado: " + tipo)
  }
}

4) Test & mockeo fácil con Factory

Cambia la Factory por un doble de prueba para aislar el servicio.

// Doble de prueba (mock/fake)
class FakeFactory {
  crear(tipo) {
    return {
      pagar: (monto) => Recibo("fake-" + tipo, monto) // comportamiento controlado
    }
  }
}

const svc = new CheckoutService(new FakeFactory())
const r = svc.cobrar("tarjeta", 123.45)
assert(r.metodo == "fake-tarjeta")
assert(r.monto  == 123.45)

5) Si alguna vez usas Singleton… (versión segura)

Que sea inmutable, thread‑safe y detrás de una interfaz inyectable.

// Config inmutable (mejor inyectarla que leerla como global)
const Config = Object.freeze({
  currency: "COP",
  region: "CO"
});

class CheckoutService {
  constructor(factory, config) {
    this.factory = factory
    this.config  = config // inyectado → testeable
  }
}
