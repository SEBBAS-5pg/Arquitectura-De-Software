¿Por qué Strategy supera a Factory para flexibilidad dinámica?

1. Tesis

El patrón Strategy resulta más crítico que Factory para garantizar escalabilidad con cambios de comportamiento en tiempo de ejecución. Strategy encapsula algoritmos como objetos intercambiables y permite seleccionar la variante en runtime sin condicionales masivos, evitando código espagueti. En contraste, Factory (creacional) oculta la construcción de objetos, pero no resuelve por sí mismo la variación dinámica del algoritmo después de instanciarlo.

2. Diferencia de categorías

  • Strategy (comportamental): define una familia de algoritmos, encapsula cada uno y los hace intercambiables sin if-else interminables. El cliente depende de la interfaz, no de implementaciones concretas.
  • Factory (creacional): centraliza la creación de objetos y promueve polimorfismo en la construcción, pero no cambia el comportamiento del objeto ya creado ni elimina ramas condicionales en ejecución.

3. Cómo Strategy previene el “código espagueti”

En lugar de tener un método con múltiples if/else o switch para decidir “qué algoritmo correr”, el contexto mantiene una referencia a la estrategia actual (por ejemplo, Simple, Por Volumen, ML) y delega la ejecución sin ramificaciones. Agregar un algoritmo nuevo solo implica añadir una clase que implemente la interfaz, cumpliendo mejor el principio Open/Closed (abrir para extensión, cerrar para modificación).

4. Strategy vs. Factory (resumen práctico)

  • Strategy: cambia algoritmos en runtime; extensible sin modificar el cliente. Limitación: requiere mantener una familia de estrategias bien diseñada.
  • Factory: encapsula creación y favorece polimorfismo de instancias. Limitación: no maneja cambios de comportamiento post-creación.

5. ¿Cuándo priorizar Strategy?

Cuando existe cambio frecuente de reglas o algoritmos (precios, promociones, cálculo de tarifas, ruteo, scoring, compresión, serialización). En aplicaciones dinámicas cumple mejor con Open/Closed que basarse solo en Factory, porque evita tocar el contexto al introducir una nueva variante.

6. Proyecto de primera aplicación

E-commerce de gran escala (pagos): los algoritmos varían por método (tarjeta, PayPal, crypto) y por condiciones de negocio (promoción simple, antifraude avanzado, ML). El tráfico y la estrategia de conversión exigen cambiar o combinar algoritmos en tiempo de ejecución sin condicionales caóticos.

  • Por qué primero: la variabilidad de reglas es alta; Strategy permite switch runtime y pruebas aisladas por algoritmo.
  • Beneficios: añadir pagos/algoritmos sin tocar el contexto; mejor testabilidad; crecimiento sin “ramas gigantes”.

7. Ejemplo conceptual mínimo

interface EstrategiaPago { procesar(pedido): Resultado; }
class Tarjeta implements EstrategiaPago { /* ... */ }
class PayPal implements EstrategiaPago { /* ... */ }
class Crypto implements EstrategiaPago { /* ... */ }

// Contexto no usa if/else: delega
class Checkout {
  constructor(estrategia) { this.estrategia = estrategia; }
  setEstrategia(e) { this.estrategia = e; }  // runtime
  pagar(pedido) { return this.estrategia.procesar(pedido); }
}
