Iteración 2: El Nivel 2 (Contenedores) y la Salud del Sistema

Continuando con el debate, hoy analizamos el Diagrama de Contenedores. Si el Nivel 1 nos decía "qué" hace el sistema, el Nivel 2 nos revela "cómo" se distribuye la responsabilidad técnica.

1. Identificación de Fallos de Comunicación

Este nivel es crítico para detectar problemas que en UML quedarían ocultos tras una línea de asociación. Al definir contenedores, podemos identificar:

  • ⚠️ Acoplamiento Excesivo: Si un contenedor (ej. Microservicio A) tiene demasiadas flechas hacia otros contenedores, estamos ante un posible "Monolito Distribuido".
  • ⚠️ Incompatibilidad de Protocolos: Permite visualizar si el Frontend en Angular intenta hablar con un Backend en Spring Boot usando un protocolo no soportado o si falta un API Gateway intermedio.

"Los componentes son unidades encapsuladas con interfaces bien definidas... fundamentales para razonar sobre responsabilidades."
— Clements et al. (2003), Documenting Software Architectures.

2. El "Single Point of Failure" (SPOF)

En el diagrama que adjunto (basado en el modelo de Simon Brown), podemos ver un API Application que centraliza todas las llamadas. Si este contenedor falla, tanto la App Móvil como la Web quedan inoperativas. El C4 Nivel 2 nos obliga a ver esta realidad física, a diferencia de los diagramas lógicos que solo muestran flujos de datos ideales.
