Iteración 3: El Nivel de Componentes y la Agilidad

Para mi tercera intervención, quiero poner sobre la mesa el nivel más polémico del Modelo C4: El Nivel 3 (Componentes). Según Simon Brown, este es el nivel donde más errores de diseño se cometen.

1. La Trampa de la "Arquitectura de Erosión"

El mayor peligro en este nivel es la erosión arquitectónica: cuando el diagrama dice una cosa y el código hace otra. En equipos grandes, los componentes (como un "Gestor de Pagos" en Spring Boot) a menudo terminan acoplados de formas no previstas, convirtiendo el diagrama en una pieza de "ficción técnica".

¿Cuándo usar el Nivel 3? ¿Cuándo omitirlo?
Sistemas complejos con lógica distribuida. Sistemas simples o CRUDs básicos.
Equipos grandes que requieren Onboarding. Equipos de < 5 devs con comunicación diaria.
Para identificar cuellos de botella lógicos. Si el código es la "única fuente de verdad".

"Solo crea el diagrama si el esfuerzo de mantenimiento vale la comunicación de diseño... hay que equilibrar el modelo con la agilidad."
— Brown, S. (2015). Software Architecture for Developers.

2. Reflexión sobre Componente vs. Clase

Es vital no confundir un componente con una clase de Java o Angular. Un Componente es una agrupación de código (un conjunto de clases bajo una interfaz) que entrega una funcionalidad. Si intentamos mapear cada clase en el Nivel 3, generamos burocracia técnica insostenible.

¿creen ustedes que en un entorno de Sprints de 2 semanas, el Nivel 3 ayuda a prevenir errores o se convierte en un obstáculo que nadie actualiza?
